# First Principles review: Candidate 1 (pre-install publisher-exposure guard)

**The problem underneath:** an AI agent adds a dependency, and that dependency might run attacker code on a developer or CI machine. The brief swaps that problem for a proxy: how many accounts can publish somewhere in the new transitive tree. The proxy is defensible, because Shai-Hulud spread by stealing a maintainer's token and republishing every package that account controlled ([Endor Labs](https://www.endorlabs.com/learn/understanding-npm-worms-and-the-shai-hulud-attack), [Flashpoint](https://flashpoint.io/blog/shai-hulud-worm-targeting-npm-supply-chains/)). But the payload ran through install scripts, and the main defences people actually use don't care how many publishers there are: disabling scripts, release-age gates, lockfiles and 2FA or trusted publishing ([sqli on pnpm vs Shai-Hulud](https://www.sqli.com/int-en/insights/pnpm-vs-shai-hulud-npm-security), [lilting.ch](https://lilting.ch/en/articles/pnpm-11-minimum-release-age-default-shai-hulud-defense), [GitHub's npm plan](https://github.blog/security/supply-chain-security/our-plan-for-a-more-secure-npm-supply-chain/)). Counting publishers is a real signal, but a weak one, and it is not the lever that matters most.

**Is the graph actually needed?** Partly. Features 1 and 2 are a transitive closure, a union of maintainer sets and a set difference. A Python dict built from `npm ls --all` plus packument lookups does that in about 40 lines. Feature 3, the worm replay, alternates package → dependents → accounts → their other packages over a two-type network, and that is graph-native. The "remove FalkorDB" test passes, but only barely, and only because of the feature the brief calls "an illustration."

## SCORES (1–10)
- **Graph essential: 6.** The Package/Account graph is real and the multi-hop alternation is honest. The agent tool itself, though, is a set difference that doesn't need a graph DB.
- **Demo memorability: 6.** "Candidate A adds 1 publisher, B adds 40" plus a spreading worm animation is clear. It is also abstract: nobody gets hacked on screen.
- **4-day feasibility: 6.** About 10k packuments at npm's 1 req/s crawler guidance ([npm crawler policy](https://docs.npmjs.com/policies/crawlers)) is roughly 3 hours, so the crawl is fine. The risks are the hook, the canvas and the replay all landing on days 2–3, plus "fetch on demand" edge cases (scoped packages, peer and optional deps, ranges).
- **Originality: 6.** [Socket MCP](https://docs.socket.dev/docs/guide-to-socket-mcp) already gives agents pre-install package scores, free and hosted. [pkgrisk](https://docs.rs/crate/pkgrisk/0.1.0) does per-package bus factor. Comparing candidates by the set of new publishers they add looks new, but the core insight is the 2019 [USENIX paper](https://usenix.org/conference/usenixsecurity19/presentation/zimmerman), which the brief rightly cites.
- **Real-world usefulness: 4.** The metric counts every maintainer as able to publish, ignores 2FA and trusted publishing (now being mandated), and only applies to fresh resolutions. The headline date-library example is weak: dayjs and date-fns have zero runtime dependencies, so the answer is obvious without a tool. Security teams already buy Socket or Snyk, and few people would act on "+40 publishers."

## WIN CHANCE (Agents That Act on Connected Data): ~5%
It fits the track well (graph queries as MCP tools, explainable paths, and an action driven by the graph), and supply-chain security hits a nerve right now. Against 100–300 real entries in the most crowded track, the judges' "who would use this over Socket?" question and the thin graph-necessity case for the core tool keep it mid-pack. A polished build is plausibly top 10%. Winning outright is unlikely. I could not find past WeMakeDevs/FalkorDB winners. The closest FalkorDB-sponsored winner I found, Atrium, used a graph of students' misconceptions, a vivid human use case ([FalkorDB blog via plushcap](https://www.plushcap.com/content/falkordb/blog/falkordb-memory-meets-motion-the-falkordb-standouts)).

## EVIDENCE
- FalkorDB supports `algo.pageRank(label, relType)` and `algo.bfs`, and warns of out-of-memory errors on large connected graphs ([procedures](https://docs.falkordb.com/cypher/procedures), [algorithms](https://docs.falkordb.com/algorithms)), so the planned queries are supported.
- Shai-Hulud 2.0 hit 796 packages through stolen tokens and preinstall scripts ([Endor Labs](https://www.endorlabs.com/learn/understanding-npm-worms-and-the-shai-hulud-attack)).
- GitHub is moving to FIDO 2FA, 7-day tokens and trusted publishing ([GitHub blog](https://github.blog/security/supply-chain-security/our-plan-for-a-more-secure-npm-supply-chain/)), which weakens the "every maintainer can publish" assumption over time.

## Simulation, briefly
Day 1: the crawl works, but range resolution (the "latest" dependency vs the `npm ls` result) gives match rates of perhaps 80–90%. Day 2: the PreToolUse hook needs to parse `npm install x y@^2 -D` variants. Day 3: the canvas and replay need tuning. Demo shot 2 is the weak point. If the real numbers come out 0 vs 3, the story falls flat. Judge questions: "Why not Socket?", "Does 2FA make this count meaningless?", "Why a graph DB for a set difference?", "My lockfile already pins this, right?", "Who has changed a dependency because of this number?" The second, third and fifth are hard to answer.

## TOP 3 FLAWS
1. **A proxy metric with no barriers modelled.** A judge asks whether a 2FA-protected maintainer of `react` counts the same as an abandoned single-maintainer package with a classic token. The answer is yes, and the credibility of the number drops.
2. **The core tool doesn't need the graph.** A FalkorDB judge points out that `compare_install` is a set difference, and the graph's real work then rests on a replay the brief itself calls "not a validation."
3. **The demo numbers may not be dramatic.** Popular candidates (dayjs, date-fns, zod) often have zero dependencies, so the comparison shows 1 vs 2 publishers and the planned "1 vs 40" never happens.

## THE BEST VERSION
Keep the MCP tool, the PreToolUse hook and the path explanations. Make the score weighted rather than a raw count: weight each account by how many packages it can publish (its blast radius, a graph quantity), add one-maintainer and recently-changed-maintainer flags, and add whether the package has install scripts (packuments expose `scripts`). Then the graph ranks risk instead of counting heads. Pick demo candidates from real data where the gap is large (for example request vs. got vs. native fetch). Cut PageRank unless it changes a decision. Present the worm replay as "accounts whose compromise reaches you," which is the graph's real value.

## VERDICT
Build it with changes: replace the raw publisher count with a weighted risk score computed from the graph, which includes install scripts, and pick demo candidates whose difference is large in real data.
